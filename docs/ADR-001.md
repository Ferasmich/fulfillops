# ADR-001 — Transactional orders and PostgreSQL work table

Status: acceptance implemented in Part 2; worker claiming, fencing, retries and crash recovery implemented and tested in Part 3.

## Context and decision

Choose Python 3.12, FastAPI/Uvicorn, explicit SQL using Psycopg 3, and PostgreSQL 16. Use pytest/HTTPX for tests, Ruff for static checks and prometheus-client for metrics. Installed Python versions are pinned in requirements/runtime.txt and requirements/development.txt. Container image digests will be pinned during container work.

Use one database transaction for acceptance and one durable work table instead of a separate message broker. This reduces solo operational scope and avoids a database/queue dual-write gap. SQL makes uniqueness and locking boundaries visible during defense. Redis Streams remains a possible alternative but would add acknowledgement and cross-store coordination work.

## Idempotent acceptance algorithm

1. Validate key (8–128 printable ASCII characters), body and original item quantities; reject booleans. Build canonical JSON from customer ID plus SKU-sorted aggregated items. Compare full canonical values, not only a hash. Different JSON key ordering and reordered/equivalent item lines are treated identically. Unknown additional request fields are rejected as INVALID_REQUEST, a documented implementation choice.
2. Pre-generate an order UUID. Begin READ COMMITTED. Attempt to insert `order_requests(key, canonical_payload, order_id)` with `ON CONFLICT (key) DO NOTHING RETURNING key`. The order foreign key is deferred until commit so the request row can be the first uniqueness gate.
3. If no row was inserted, read the existing mapping in a separate statement in the same transaction. A conflicting insert waits for the first transaction's commit/rollback; the next READ COMMITTED statement sees its committed mapping. Compare canonical payload: return its queued receipt on equality, otherwise 409 IDEMPOTENCY_CONFLICT. Never reserve in this branch. Rollback by the first requester permits a competing insert to become the new owner.
4. For a new key, lock requested products using `SELECT ... ORDER BY sku FOR UPDATE`. Lock in deterministic SKU order to reduce deadlocks. Check missing SKUs and all stock before updating any row.
5. On insufficient stock, roll back the complete transaction, including the temporary key mapping. The chosen policy does not retain keys for rejected orders; only accepted requests acquire durable mappings.
6. Insert order and aggregated order items, decrement products, and insert one work row. Commit before emitting 202. The deferred key foreign key must resolve at commit. Any error rolls everything back.
7. Bound database waits and use a small bounded whole-transaction retry for deadlocks/transient transaction failures. A retry must preserve the key/payload; do not blindly retry after an unknown commit result with a fresh key. Reconnect and replay the same key.

## Job lifecycle and fencing

Proposed lab defaults: five maximum attempts, ten-second claim lease, one-second polling, exponential retry delays of 1, 2, 4 and 8 seconds. These are design choices to be tested and tuned, not measured recovery promises. The simulated business operation is short; if processing may exceed a lease, renew ownership conditionally using its current token.

Claim transaction: select a due queued job or expired processing job with `FOR UPDATE SKIP LOCKED`. If attempts have already reached the maximum, atomically mark job and order failed and retain stock; this also handles a crash during the final attempt. Otherwise increment attempts, issue a new UUID claim token, set lease expiry using database time, record the attempt and set order/job processing. Commit before doing processing.

Completion transaction: lock the job row and recheck its processing state, exact token and unexpired lease using database clock time after lock acquisition. A stale owner must discard its result. Insert one completion receipt with `order_id` as primary key, and change order/job to completed in that same transaction. Do not decrement inventory during completion. No external side effects are performed outside this protected database outcome.

Failure transaction: lock and verify the same ownership conditions. Save only a safe failure category. If attempts remain, set queued and next available time, clearing active ownership; otherwise set both job/order failed. Never delete the order or automatically restock. An expired owner cannot mutate retry state. Reclaim closes a crashed attempt before recording the next attempt. Each claim increments the persistent count, including crashes.

Poison injection is a test-fixture-only mechanism tied to an isolated test database; do not add an admin/reset/poison HTTP endpoint. Persist attempts and outcomes for audit. Operator review is initially documentation and database inspection; no automatic redrive/restock is in scope.

## Tradeoffs and limits

Polling adds small database load and pickup latency. Leases balance recovery delay against false reclamation. Fencing prevents stale completion but needs a dedicated race test. The database remains a single local dependency; persistent volumes are not high availability or backups. Runtime roles must not perform DDL or reset databases. These decisions reduce infrastructure complexity without reducing the required evidence.
